# writing-review

審查 `blog-app/src/content/blog/*.mdx` 的文章，判斷能不能收工。

判準來源是既有規格，不是這份檔案自創的：`CLAUDE.md` 的「寫作慣例」與 `writing/WRITING-PLAYBOOK.md`。
兩份有衝突時以 `CLAUDE.md` 為準。動筆審之前先讀它們——規範會改，不要靠記憶。

## 怎麼審

逐條檢查，每一條都要指出**具體是哪一段**。找不到問題就明講「這條通過」，不要為了湊數挑毛病。

### A. 硬性違規（違反就是不通過，沒有討論空間）

| 檢查 | 不通過的樣子 |
|---|---|
| 內部資訊 | 出現產品截圖、客戶名、Jira／PR 編號、Figma 檔名、內部元件名、AI 模型型號 |
| 客戶專案紅線 | 寫到產品細部結構、資料模型、欄位來源、需求優先度、客戶決策 |
| 沒有佐證的數字 | 天數／次數／字數對不上 log 或 commit，又沒標 TBD |
| emoji | 內文灑 emoji（只有號召讀者行動的段落可以有） |
| 標題階層 | 用了 `##`（技術示範類文章除外），或沒有從 `###` 起跳 |
| 前言／結語 | 出現「前言」「結語」「總結」當標題 |

### A2. AI 味（草稿一產出就先掃這一輪）

這六條是最常犯的。掃到就直接改，不要只標記——改法一律是「換回作者實際會講的話」，不是換一組同義詞。

| 徵狀 | 長什麼樣 | 改法 |
|---|---|---|
| 對仗與排比 | 「不只是⋯更是⋯」「既要⋯也要⋯」 | 拆成兩句普通的話，或只留有資訊的那半句 |
| 三段式總結 | 每節結尾補一句把剛講完的再講一次 | 刪掉。作者的習慣是用內容自然收尾 |
| 轉折詞開頭 | 「然而」「因此」「值得注意的是」連續出現在段落開頭 | 直接進句子，中文口語不需要這些接頭 |
| 形容詞堆疊 | 「高效」「強大」「顯著提升」但沒有數字或實例 | 換成實際發生的事與量到的數字，量不到就刪 |
| 結論被泛化 | 從「我這次遇到的狀況」滑成「在當今 AI 時代，我們都應該⋯」 | 收回第一人稱的具體情境 |
| 沒有第一手細節的建議 | 讀起來對、但作者沒做過 | 查 log／commit；查不到就整段刪，不要留著充數 |

判準是**這句話 Abby 講得出來嗎**。講不出來就是 AI 味，不管它多正確。

### B. 寫作慣例

1. **開場**——有沒有直接進情境？是情境提問或共感提問，不是背景交代
2. **「prompt 怎麼下」有沒有被寫壞**——只放最後那版漂亮的 prompt 就是寫壞了。必須有：第一次下的 prompt 是什麼 → 為什麼不行 → 改了哪裡才 work
3. **有沒有藏失敗**——「什麼順、什麼卡」的對照還在嗎？承認做錯的段落有沒有被縮成 blockquote 附註（那該升格成正式一節）
4. **有沒有誇大 AI**——結論該有邊界（「AI 不會取代 X，但能讓沒有 X 的團隊跨過門檻」），不是 AI 萬能
5. **語氣**——有沒有中二感或過度自信？被改掉過的字：終於／崩潰／靈魂／哲學／最關鍵／最痛／打臉／敢。目標是「跟同事分享成果報告」
6. **中英混用**——Prototype、Flow、Component 這類詞有沒有被「修正」成純中文？不該修
7. **自嘲有沒有被專業化掉**——降低門檻的句子（「我並沒有用什麼厲害的技術」）要留
8. **粗體用法**——粗體該是「可獨立成立的一句話結論」，不是拿來標關鍵詞
9. **結尾**——是不是「給同處境者的建議」，1/2/3 編號、每點粗體短句起頭？固定簽名在不在？
10. **標題**——只有讀過這篇的人才寫得出來嗎？「踩過的坑」「難的不是 X」這種萬用詞換一篇也能用，不算數

### C. 改稿紀律

- **同一組結論全篇不超過兩次**（開頭 TL;DR ＋ 結尾清單，頭尾呼應就夠）
- **最原創的那節不要排在 60% 的位置**
- **名詞解釋不要擋在最前面**——拆成首次出現時的括號註解，或挪到文末

### D. 雙讀者視角

用兩種讀者各讀一次，各項 1–5 分：

- **讀者 A（目標讀者）**：做 AI 相關 UI/UX、正在學 vibe coding 的設計師。看代入感、方法能不能帶走
- **讀者 B（跨領域／內容編輯）**：懂產品設計但不是深度 AI 工作者。看沒有背景的人看不看得懂、哪裡無聊、哪裡需要圖

評分項目：像不像人寫的／讀起來順不順／有沒有代入感／建議有沒有用／視覺節奏是否足夠。

**通過門檻**：兩位整體都 ≥ 4/5，兩位「像不像人寫的」都 ≥ 4/5，且 A 區沒有任何一條違規。

## 輸出格式

不通過時，每個問題寫成三行，不要寫成散文：

```
段落：<引用該段開頭 15 字，或標題名稱>
原因：<違反哪一條，一句話>
調整方向：<具體怎麼改，不是「建議加強」這種空話>
```

然後**直接動手改**，不要只報告完就停。改完重審。

通過時輸出一行 `PASS` 加上兩位讀者的評分，然後**一定要跑這行把通過狀態記下來**，否則 Stop hook 會再擋一次：

```
.claude/hooks/writing-review-gate.sh pass <文章路徑>
```

## 不要做的事

- **不要把 `<strong>` 改成 `**`。** 中文標點緊接粗體結尾時（例如 `**Level 1｜反應式。**我說…`），
  CommonMark 的右側界定規則會讓 `**` 失效，字面符號直接噴到畫面上。
  `ai-agent-autonomy-levels.mdx` 用 `<strong>` 是刻意的，不是風格不一致。
  2026-08-27 誤判過一次：換掉 20 處之後渲染只剩 5 個粗體、畫面出現 60 個字面 `**`。
- 不要把中英混用「修正」成純中文
- 不要刪掉承認失敗或不確定的句子
- 不要為了「更完整」加上作者沒實際做過的建議
- 不要因為找不到問題就硬挑一條來寫——通過就說通過
