## 種子 1：從「我的部落格能不能被問答？」到「我真正缺的是編輯與發布環節」

**角度**  
不是再做一個 RAG，而是重新釐清 Abby.log 的產品定位：它不是一般內容站，而是把實作過程、判斷、踩坑與工作流整理成可被閱讀、可被求職展示的「思考證據庫」。

**為什麼值得寫**  
今天的材料裡有一個很清楚的轉彎：一開始是看到別人的 blog 問答互動，想知道原理；後來發現問題其實不是「文章能不能被問」，而是「自動撈題 → 寫成文章 → 快速審稿 → 小修 → 發布」中間斷掉。  
這很適合寫成一篇 Abby.log 的產品反思文：  
- 為什麼小型 blog 現階段不一定需要 RAG  
- 為什麼真正有價值的是把工作過程變成可讀材料  
- 為什麼 AI 幫忙寫完後，仍需要一個人類能快速判斷好壞的編輯介面  
- blog 與 portfolio 到底要不要合併：不是版型問題，而是「我想展示什麼能力」的問題

注意：不要寫出內部 repo 結構、未發布草稿檔名、具體自動化排程細節，只保留「流程斷點」與「產品判斷」即可。


## 種子 2：自動化有在跑，不代表工作流有出口

**角度**  
今天很明顯出現一個重複模式：上游自動化其實有正常產出，但產物沒有進入 Abby 會看的地方，於是「有做」等於「沒被使用」。這可以寫成一篇關於個人 AI 工作流的文章：自動化的價值不在於它跑了，而在於它有沒有接到人的決策介面。

**為什麼值得寫**  
這題和 Abby 之前寫過的「自動化的出口問題」是同一個母題，但今天的角度更具體：  
- 出題自動化、寫作自動化、審稿自動化都不是終點  
- 真正的產品問題是：結果去哪裡？誰會看？看完能不能立刻處理？  
- 一個 AI 工作流如果沒有「落地點」，就會變成另一個資料垃圾桶  
- 對個人知識系統來說，出口設計比資料蒐集更重要

**素材來源**  
今天對文章種子、草稿、發布狀態、工作流斷點的檢查；以及 memory dashboard 中「工作狀態 vs 實際行為」的設計脈絡。

**公開風險**  
低到中。概念可以公開，但要避免列出實際輸出位置、排程 ID、內部資料夾、具體未發布文章清單。  
建議寫成通用工作流反思，不寫成「我哪個資料夾裡堆了多少份」。


## 種子 3：不是每個偏好都該寫進記憶：事件觸發要用 hook

**角度**  
這題可以寫給正在做 AI agent / Claude Code / Hermes 工作流的人：  
「我希望 AI 以後自動做某件事」不等於「把偏好寫進 memory」。如果那件事要在某個事件發生時自動執行，就應該進 hook；如果只是讓 AI 回答時知道你的習慣，才是 memory。

**為什麼值得寫**  
這是很實用、也很容易踩坑的 AI agent 配置常識。  
可寫成一篇短文或教學筆記：  
- memory 是背景知識，不會自己觸發行動  
- hook 是事件反應機制  
- 「寫完檔案後格式化」、「compact 前提醒」、「跑命令前記錄」這類需求都不是記憶問題  
- 把自動化需求錯放進 memory，會造成期待落差：你以為它會做，但它只是在下次對話裡「知道」這件事

**素材來源**  
今天的 Claude Code / Hermes 設定討論與 config skill 內容。

**公開風險**  
低。屬於通用 AI 工具使用方法。  
注意：不要貼出個人設定檔內容、實際 hook 路徑或本機環境細節。
