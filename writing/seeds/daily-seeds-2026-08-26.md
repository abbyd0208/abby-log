## 種子 1：搜尋 0 筆不等於沒問題——AI 稽核為什麼要先驗證「搜尋本身有效」

**角度**  
從 AI 協作裡很常見的誤判切入：工具回傳 0 筆，模型就很容易直接下結論「沒有問題／已修好」。但有時候錯的是搜尋語法、掃描範圍或工具能力，不是系統真的乾淨。

**為什麼值得寫**  
- 很適合 Abby.log：是 AI 工作流裡的真實踩坑，不依賴客戶產品背景。
- 可以整理成一套可複製的稽核流程：  
  1. 先用寬鬆查詢確認搜尋工具有命中能力  
  2. 再縮小條件  
  3. 每條結論附可重跑指令與原始輸出  
  4. 不能重現就標 UNVERIFIED
- 對使用 Claude Code / Hermes / Codex 做 code audit 的人很實用。

**素材來源**  
近期工作流收件匣中的規則候選與稽核方法沉澱；內容是通用 AI 工作流，不需要引用客戶產品、專案代號或內部文件。

**公開風險**  
低。只要不要放原始專案、分支、PR/Jira、設計 token 具體名稱，就可以公開。建議用「一次 design token 稽核」這種抽象描述即可，不要寫實際產品背景。

## 種子 2：共用 repo 裡的 AI 協作邊界——哪些 Claude Code 規則可以進 git？

**角度**  
很多團隊開始把 AI agent 規則、hook、專案記憶放進 repo，但「進 git」其實等於「對全隊生效」。這篇可以寫成：個人設定、團隊設定、local override、hook、專案規則各自該放哪裡，以及什麼東西不該默默 commit。

**為什麼值得寫**  
- 很符合 Hermes / Claude Code 工作流主題。
- 有清楚的讀者痛點：想讓 AI 照團隊規則工作，但又怕污染別人的環境或引入安全風險。
- 可以變成一篇實用指南：  
  - 個人設定 vs 團隊設定  
  - `CLAUDE.md` / `AGENTS.md` 的角色  
  - hook 腳本與設定檔要一起 review  
  - 判斷題不要硬擋，客觀錯誤才 block  
  - 生成索引不要手寫

**素材來源**  
近期 Claude Code / Hermes 系統設定筆記，以及 memory-dashboard README 裡對「個人儀表板、session、專案狀態」的說明。

**公開風險**  
中低。主題本身可公開，但原始素材來自實際團隊 repo 操作，撰寫時必須完全拿掉：客戶名、repo 名、檔名、hook 實際內部路徑、具體產品文件例子。  
建議寫成「我在整理共用 repo 的 AI 規則時踩到的三條邊界」，不要寫成某專案案例復盤。

## 種子 3：個人 AI 記憶儀表板：把「我說我在做什麼」跟「我實際動了什麼」分開看

**角度**  
從 memory-dashboard 的設計切入：個人工作狀態其實有兩層——  
- 意圖層：我記憶裡說我正在做什麼  
- 行為層：session 檔案實際顯示我最近動了什麼  

這篇可以寫成「我怎麼用本地儀表板減少工作狀態失真」。

**為什麼值得寫**  
- 是 Abby 自己的 AI 工作流方法，跟客戶產品無關。
- 和既有「記憶系統」題材相連，但角度更具體：不是只講記憶，而是講工作狀態可視化。
- 可以把 dashboard 的幾個設計判斷寫出來：  
  - 不假裝知道 session 是否真的開著，只標「最後活動」  
  - session 原文含私密資訊，所以資料層不進 git  
  - 手動標記與自動弱比對並存  
  - 記憶 N 天沒更新 ≠ 一定過期，只是提醒

**素材來源**  
memory-dashboard README、build 腳本說明、近期自動生成資料層。

**公開風險**  
低到中。概念可公開，但不能展示真實 session 清單、專案名稱、branch、任務原文。若要配圖，建議做假資料 mock，不用真 dashboard 截圖。
