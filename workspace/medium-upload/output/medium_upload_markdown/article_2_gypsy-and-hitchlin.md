## 從一個助理到一個團隊

前面那篇文章講的是儀表板——一個設計師想看清自己的 AI 在幹什麼。那是單一助理的故事。

但故事沒有結束。

半年前，我也只有一個全能的 Claude Code 助理。它分身乏術，什麼都要我決定，什麼都要在一個對話裡推進。效率好不到哪去，每一次對話都得重新載入上下文，講一堆廢話。

所以我開始試驗：如果把工作分給不同的 AI 助理，各司其職，會不會更快？

答案是會的。但怎麼分，分給誰，這裡面有套路。

## 認識吉普賽和哈奇林

我現在用兩個主力助理：

**吉普賽（Hermes Agents）** 負責後台的自動化——掃檔案、更新記憶、寫日誌、檢查工作狀態。它的職責清單寫死了，任務來的時候就按步驟走。我給它取名「吉普賽」，因為我想要它像流浪者一樣靈活，在各個系統間來去。Hermes 在希臘神話裡本來就是信使神，這個名字蠻貼切的。

**哈奇林（Claude Code）** 負責前台的創意工作——寫文章、設計方案、解決問題。它可以質疑我的要求、提出新想法、跟我即時互動。我給它取名「哈奇林」，純粹是喜歡這個音。它代表一種更「人」的互動——有個性、會抱怨、有主見。

吉普賽負責看不見的管道，哈奇林負責看得見的對話。一個重複性，一個創意性。一個冷，一個熱。

## 吉普賽的工作流——自動化記憶

我在 Slack 上接了 Hermes，幫它設定了一份工作清單。每天的固定時間，吉普賽就會：

1. **掃描昨天的對話日誌**
   - 從 Git 倉庫拉取哈奇林寫下來的記憶檔
   - 找出「今天完成了什麼」「遇到什麼問題」「下一步是什麼」

2. **更新中央記憶庫**
   - 把新學到的東西融入我的「準則檔」
   - 更新「進行中的專案」清單
   - 整理「已解決的問題」歸檔

3. **生成每日摘要**
   - 寫成 Markdown，存進 daily-log
   - 這個檔案會被儀表板讀取，顯示在我的個人面板上

4. **檢查自己有沒有故障**
   - 記錄每次執行的時間戳和成功/失敗狀態
   - 這就是上一篇講的「狀態列」——我要知道它有沒有在跑

最妙的地方在於：**吉普賽會自動修正自己的記憶**。

Hermes 有個特性叫「skills」，就是它學過的東西。每一次成功執行，它會看看「這次我是怎麼做的」，有沒有可以優化的地方。比如說，如果我的檔案結構改了，它不會卡在舊路徑上——它會自動試新路徑，然後把成功的方案記下來。

## 怎麼設定 Hermes + Claude Code

如果你也想試，這邊是基本的設定邏輯：

**第一步：在 Slack 接 Hermes**

Hermes 有官方的 Slack 整合。加上去之後，它就可以在 Slack 上接指令——`@hermes do something` 這樣。我給它一份「定期任務清單」，用 cron 語法定時執行。

設定檔看起來像這樣（簡化版）：
```yaml
schedules:
  - name: "daily-memory-sync"
    time: "23:59"  # 每天晚上 11:59
    task: "scan-conversations"
  - name: "morning-briefing"
    time: "08:00"  # 每天早上 8:00
    task: "generate-summary"
```

**第二步：連接 Claude Code**

Claude Code 有 Git integration。我的做法是：每次 Claude Code（哈奇林）更新記憶檔，它自動 commit 到一個私有倉庫。吉普賽每天早上去拉這個倉庫，看看昨天的進度。

這樣做的好處是：
- 版本控制：我可以看見記憶是怎麼演進的
- 履歷追蹤：哪些改動有效，哪些沒效
- 備份：記憶不會只存在一個地方

**第三步：定義各自的職責**

在 Hermes 的配置裡，我明確寫下吉普賽的「可以做什麼」。比如說：
- 可以讀取檔案、更新檔案，但不能刪除
- 可以在 Slack 上發消息，但不能改我的待辦清單
- 遇到決策題（「要不要關掉這個專案？」）就停下來問我

在 Claude Code 的 instructions 裡，我寫下哈奇林的邊界：
- 創意工作優先於重複工作
- 有疑問就問，不要自作聰明
- 每次記憶更新都要註明「為什麼改」

## 為什麼要分成兩個？

有人會問：一個聰明的 AI 做不了嗎？為什麼要分？

我的經驗是：不行。

原因很簡單——專精和通才是兩回事。哈奇林（Claude Code）很擅長上下文切換、理解模糊的需求、生成創意內容。但它不適合重複執行結構化任務。每次它做重複工作，都會燒掉一些 token，還容易漂移（今天的執行和昨天的執行會有細微差異）。

吉普賽（Hermes）則反過來。它的優勢在於：
- 嚴格執行流程（不會臨時改變主意）
- 低延遲（排程任務不用等人，立刻跑）
- 持久化的狀態（能記得上次執行的細節，這次要從哪開始）

分工以後，吉普賽只負責「檔案同步」「狀態監控」「記憶更新」，不會亂想。哈奇林只負責「創意輸出」「問題求解」，可以盡情發揮。

效率提升大約三倍，至少感覺上是。（我沒量，就是感覺。）

## 記憶管理的三個層級

這套系統運作起來後，我發現記憶其實分三個層級：

**第一層：實時記憶（Hermes + Claude Code 當中的對話）**
- 一個對話進行中的上下文
- 範圍最窄，最鮮活
- 對話結束就會被新對話頂出來

**第二層：持久記憶（Git 裡的檔案）**
- 我的準則、進度、學習筆記
- 每次新對話時自動載入
- 由吉普賽定期整理和更新

**第三層：可視化記憶（儀表板）**
- 人能看到的東西
- 我最在乎的那一層
- 設計重要性遠超「儲存」本身

三層缺一不可。實時記憶再好，沒有持久層就會遺忘。持久層再完善，沒有可視層就等於沒有。

## 目前還在摸索的地方

一個月用下來，我發現還有幾個沒解決：

1. **記憶的「遺忘」機制**
   - 準則檔越來越肥，什麼都放進去
   - 需要一個「什麼時候該刪掉舊東西」的規則

2. **多代理間的溝通成本**
   - 吉普賽寫的東西要讓哈奇林能讀
   - 哈奇林寫的東西要讓吉普賽能解析
   - 格式統一也是一種設計

3. **優先級的動態調整**
   - 現在的任務清單是寫死的
   - 理想狀態應該是吉普賽看著我的行為模式，自動調整頻率

但這是長期的課題。目前為止，雙代理系統已經大幅改善了我跟 AI 的協作體驗。

## 當機器開始學習自己的記憶

我最近注意到一個有趣的現象。吉普賽在執行「更新準則檔」這個任務時，開始會寫註解：

```markdown
## Updated 2026-08-01 by Hermes
Why: Claude Code requested clarification on edge cases in handling async tasks
Changed: Added 2 new rules under "Async Patterns"
Confidence: 87% (based on successful completions since change)
```

沒有人教它這樣做。它就是自己開始做了。

這讓我想到：**記憶的問題不只是「怎麼記」，還有「怎麼知道記對了」**。

Hermes 開始用「成功率」來判斷某個準則是不是有效。如果某條規則用了一百次，九十八次成功，它就會變成「high confidence」，優先加載。反之，如果某條規則成功率掉到 50% 以下，它會標記成「needs review」，下次對話時拿出來問我。

這是自動化最美妙的地方——不是機器在執行你的計畫，而是機器開始思考「這個計畫行不行」。

## 結語：把記憶變成協作

一個月前，我以為記憶的終點是「完整的檔案系統」。

現在我知道，那只是開始。真正的記憶系統應該是活的：
- 會自我檢驗（我上次說的規則還對嗎？）
- 會自我進化（怎麼樣用得更好？）
- 會向人類可視化（我現在卡在哪裡？）

吉普賽和哈奇林的組合，讓這些變成了可能。

AI 工作流不只是「怎麼讓機器更聰明」，更關鍵的是「怎麼讓機器和人的記憶同步演進」。那才是真正的放大效應。

我還在摸索。但已經有點不一樣了。
