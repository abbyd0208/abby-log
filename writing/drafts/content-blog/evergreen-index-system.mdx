如果你手上有一個會跑好幾輪的專案，大概都寫過一份進度總表：現在幾條線在跑、各自卡在哪、下一步是誰。我也寫了一份，而且寫得算勤。

那天我打開它，上面有一整輪的工作看起來像沒做——實際上早就做完了。那份任務清單十二天沒有回去對過，而在那十二天裡，我（還有幫我做事的 AI）都是照著它在判斷「還有什麼沒做」。

這篇記錄我後來怎麼改，以及我到現在還沒改完的那一半。

### 問題不是我懶得更新

一開始我以為這是紀律問題：下次記得更新就好。但同樣的事在不同地方又發生了幾次——

- 決策散在各場會議紀錄裡，被推翻的那幾條在另一份文件用註記標著。想知道「上個月那個決定現在還算不算數」，得自己把兩邊接起來。
- 需求文件分成設計版和施工版，只有其中一種有目錄。「某個需求的文件在哪」沒有單一答案。
- 前後有五套編號並存，每一套都有它當時的脈絡，但沒有任何一個地方寫它們的對照關係。

把這幾件事擺在一起看，共同的根因只有一句：

**同一個事實只要被手寫在兩個以上的地方，它遲早會不一致。**

不是因為誰不認真。是因為第二份副本從產生的那一刻起，就開始等著跟第一份分岔。

### 我換掉的不是格式，是誰維護索引

所以我把工作區的東西重新分成兩類，界線很硬：

**真相，寫在各檔自己的檔頭。**每一份文件在最上面用一小段 front-matter 宣告自己是什麼：ID、日期、類型、這份文件裡拍板了哪些決定、有沒有推翻先前的哪一條。人只維護自己那一份，而且那份就是原始宣告，沒有上游可以偏離。

**索引，全部由腳本生成。**決策台帳、目錄、可以點開來看的 HTML 檢視器，都是掃過所有檔頭之後產出來的。

差別在最後一句話：**生成的索引不會寫錯，因為它從來沒有被人寫過。**

我寫的是一支 Python 腳本，用標準函式庫、零依賴（這個專案沒有 build 系統，我不想為了一份索引引進一整套工具鏈）。但腳本不是重點——重點是那份索引不能是人打出來的。你用什麼東西生成它都可以。

### 三條硬規則

真相分散之後，會冒出一個新問題：舊文件怎麼辦？寫的時候是對的，過兩週被推翻了，要不要回去改？

我的答案是不要。這三條是一起成立的：

**① 寫完的檔案就凍結，狀態永遠不回改。**

決策 A 被決策 B 推翻的時候，由 B 那份文件宣告「我取代了 A」，A 那份檔案一個字都不動。A 現在還算不算數，由腳本反推，只存在於生成物裡。

好處是任何一份舊文件，都跟它當天的會議逐字稿對得起來。代價是「A 現在還算不算數」不能只讀 A，得去查台帳——這是我刻意選的：**查台帳是一個動作，維護兩處一致是永遠的負擔。**

**② 產出的資料夾只增加，不重組。**

前一次重整資料夾，我修了八十幾處相對路徑引用。那個成本不該再付第二次。所以同一個需求跨好幾輪的時候，我不靠搬檔案把它們聚在一起，靠台帳上同一個需求 ID 把它們串起來。

**③ 編號發出去就不能改。**

新的工作照統一規則命名，舊的那五套編號一律不回改，在檔頭多開一個「別名」欄位對照。這樣搜舊編號找得到新 ID，舊會議紀錄跟逐字稿也還對得上。

### 檢查腳本抓的每一條，都是我踩過的坑

腳本除了生成，還有一個只驗不寫的模式。它會檢查的東西全部有出處：

- ID 重複——手動編號遲早撞號
- 宣告取代了一個不存在的 ID——斷鏈，台帳上會變成孤兒
- 檔頭宣告了某個決策，但正文找不到對應段落——檔頭跟內文開始漂移
- 生成物裡的相對路徑指向不存在的檔——就是前面那八十幾處失效路徑的自動版
- 必填欄位缺漏——掃不進台帳，等於這份文件不存在

還有一條規則我覺得比腳本本身有用：**會變動的狀態不進檔頭。**

「這份文件對應某個合併版本」是靜態事實，寫進去沒問題；「這個版本合併了沒、落後主線多少」是會變的，一律由腳本當場去查。我以前在總表開頭寫過一條「狀態欄一律實查回填，不要憑記憶手填」——那時候它只是一句自律，現在它是機器在執行。

### 我刻意沒做的兩件事

**沒有掛排程自動跑。**這件事我猶豫過。自動化的好處很明顯，但這份索引一生成就會被我和 AI 當成現況依據，我想保留一個「生效之前人可以攔下來」的位置。所以是手動跑，然後在專案的規範文件裡寫清楚什麼時候要跑。

**沒有把「現在卡在哪」也改成生成。**像「這組按鈕不搭、方向要重想」這種判斷，腳本生成不出來，也不該被丟掉。所以總表現在是混的：敘述那段是人寫的，決策現況那塊是生成的，中間用標記隔開。

### 這件事我只做完一半

老實說，開頭那份害我誤判的進度總表，到現在還是手寫的。

原因是把二十幾份需求文件補上檔頭的時候，一定會撞到一堆內容過期需要重新對帳——那些文件的正文還在描述舊狀態。內容對帳是另一件事，混進來這輪就收不了尾。所以我先做了決策那一半，進度總表那一半延後。

也就是說，**我現在的狀況是「決策不會過期了，進度還會」。**寫下來有點尷尬，但這比宣稱我已經解決了誠實一點，而且它剛好說明了這套東西是怎麼長出來的——一次換一塊，不是一次換完。

### 給同處境者的建議

1. **先找出被你手寫兩次的那個事實。**不是找最亂的資料夾，是找同一件事出現在兩個地方的地方。那個地方就是你下一次誤判的來源，其他的通常只是看起來亂而已。
2. **把「誰維護」寫進規則裡，而不是靠自律。**人只維護自己那一份、索引一律生成——這條界線劃清楚之後，「忘記更新」就不再是一種可能發生的錯誤，因為根本沒有那個可以忘記的動作。
3. **舊檔就讓它錯著。**回頭改舊文件的狀態，看起來是在維持整潔，實際上是在讓歷史跟當初的紀錄對不起來。後面推翻前面的，讓後面那份自己宣告，前面那份留著當時的樣子。

以上感謝收看～ 如果你也在管一個會一直長大的工作區，歡迎留言聊聊你怎麼防索引過期。

與AI 的工作流就是一個不斷優化與學習的過程，同一個領域的人，面對這種靈活的工具，使用的方式也不盡相同。

透過各種不同實驗，享受各種新發現、讓工作流程更順暢，讓自己不要陷入過度的資訊焦慮，共勉之！
