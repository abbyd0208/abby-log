# 接到聽不懂的會議紀錄，第一步不是查競品

- 日期：2026-07-27（prompt 討論）→ 07-28~30（實際跑完）
- 觸發（哪件意外讓我想記）：最近接手一個給專利律師用的平台專案。參與跟客戶討論的會議時發現，他們太習慣自己的工作流程了，會很自然地講出一些專有名詞——而且**他們解釋的時候我還是聽不懂**。不是他們講得不清楚，是那些詞背後有一整套我沒有的工作經驗。

## 我做了什麼

接了一個專利／法律領域的產品案。客戶會議紀錄裡有一堆我不懂的詞——`casebook`、「分館」、`Practical Law`、OA、審查基準、判例 casebrief——而我不懂這些詞，就沒辦法決定介面該長什麼樣。

原本的直覺是去查競品、翻法律網站。跟 prompt tutor 討論後整套翻掉，變成兩輪、有先後的 prompt：

1. **第一輪 詞義盤點**：把手上的會議紀錄榨乾，逼模型先原文引用再解釋，並把每個詞分類成「A 說話者的類比／黑話｜B 業界通用詞｜C 產品自造詞」——**分類決定該去哪查**
2. **第二輪 畫面 pattern**：拿第一輪抽出的「隱含的介面結構」當輸入，去找結構相同的介面 pattern（不是找同產業競品）

然後拿真實會議紀錄跑了一次過夜任務，產出名詞盤點表、「只有客戶能回答的問題清單」、user flow 報告與流程圖。

**核心機制：定義權在誰手上，決定你該去哪查。查錯地方＝拿到正確但無用的答案。**

`casebook` 是 A 類。Google 給你「美國法學院的判例彙編教科書」——沒錯，但客戶是拿它當**心智模型的類比**在解釋「文件庫該長什麼樣」。用外部定義去設計，會做出一個電子書閱讀器，而他要的是「topic 目錄 → 案例 → 注意事項 → 檢查項目」這條抽取鏈。

## prompt 第一版

```
這是上禮拜我跟客戶討論的會議記錄，裡面有提到一些專有名詞，舉例像 casebook 這個。

我如果不懂他在講什麼的話，就沒有辦法設計這些介面。
我應該要怎麼樣做才可以瞭解？是去找競品嗎？還是去翻法律的相關網站？
```

為什麼不行：
- **沒說「以文件為準」** — 模型的訓練知識會很順地補一個聽起來很對的定義，把說話者當下的定義蓋掉，而且蓋得看不出來
- **一次只問一個詞** — 剩下十個我還不知道自己不知道
- **問錯層次** — 這不是研究問題，是抽取問題。定義就在我手上那份文件裡，客戶整段講完了

改了哪裡才 work：
- **資料放最前、指令放最後**（長文件時指令會被稀釋）
- **「先原文引用⋯再說明」** — 引用為空，我當場就看得出「文件真的沒講」，而不是被腦補的定義騙過去
- **「掃過全文每一節，包含表格、action items 與附註，不要只挑前面幾段」** — 不明說 scope，模型會自己挑覺得重要的段落
- **「文件沒講清楚就寫『文件未定義』，不要用你的一般知識補」** — 講「要做什麼」而不是「不要做什麼」
- **A／B／C 分類** — 把「要不要查競品」從直覺判斷變成可執行清單：B 才外求，A 進「問客戶」清單
- **「先講你的判斷依據，再給結論」** — 擋先射箭再畫靶
- **「不要列你不確定實際長相的產品」** — 擋憑印象生成的假競品
- **「有工具可用就先搜，搜不到再靠推理，並標明哪些是推理」** — 擋有 MCP 卻整段腦補

## 我做錯的事

> 「所以我在這個任務上的執行順序有一點錯了。原因是因為我覺得第一次跑的結果我沒有把握，所以我才進了第二次的研究。」
> —— 我自己在對話裡的原話，2026-07-29

（當時的回覆不同意這個定位。它指出：第二輪研究並沒有推翻第一輪，新增的三項都是細化不是反轉；真正缺的那塊從頭到尾都是「沒有真人用過」，而**再多的桌面研究都補不出使用者證據**。所以教訓比較接近「動手前先盤點手上已有什麼」，而不是「研究要排在建造前面」。）

> 「為什麼你在版面 review 的時候沒有抓到這個錯誤？」
> —— 2026-07-29，內文字級小於 14px 這種基本問題，自動 review 整輪沒抓到

我的解讀：

**這不是執行順序的錯，是我應該更早開始做這段研究。**

我之前只是想辦法用 UI/UX 的方式去符合客戶提出的需求。但功能越做越深入，我發現：如果沒有真正去了解律師平常看的是什麼、他們口中那些名詞到底長什麼樣（casebook 是什麼、什麼叫「答辯狀」），憑空做出來的 prototype 或介面元素，根本不會是客戶想要的。

**最具體的一次**：客戶只是很簡單地說「上傳這份判決書之後要形成摘要、產生 checklist」。但當我真的去研究他們提供的檔案、去看判決書本身的頁面結構，才發現還有很多資訊需要被抽取出來——那些客戶沒講，因為對他們來說太理所當然了。

至於字級那件事，我還不確定要怎麼歸因：是我的 design system 源頭有 bug 沒被抓到，還是「內文不得小於 14 級」這件事根本就沒有被定義？如果是後者，那我要回去把 DS repo 的文件補上字級的定義。

> 📌 查證結果（2026-07-31）：DS 有定義 **body 預設 `textSize-2`＝14/20**，`textSize-1`（12px）的用途註明是 **Caption / badge**，也明文禁止自己塞 `text-[13px]` 這種 scale 外的值。
> **但沒有任何一條寫成「內文不得小於 14px」。** 也就是說「12px 用在內文」是**用途錯誤、不是數值違規**——review 掃 token 合法性掃不出來。缺的是用途規範，不是尺寸規範。

## 兩個意外的發現（都在盤點過程中掉出來）

1. **客戶對他自己給的參考書，記錯了一個關鍵結構。** 他說「注意事項」是掛在主題層、由多份文件收斂而成；實際翻那本書（713 頁，第 4 章 129–133 頁），注意事項是掛在**判決層**、一則判決一組、不跨文件合併。也就是說他要的東西比他引用的範本更進一步——**這個差異只有真的去翻書才會發現，而它直接決定資料模型**
2. **最高優先的那題客戶問題，是讀他給的參考書才問得出來的。** 書的 Editing Notes 明講判決文經過大幅刪節、不可作為權威來源、要引用請查官方版本。那我們的文件庫存的是全文還是節錄？介面要不要標示？——**律師拿節錄本去寫書狀會出事**，這不是設計師能替客戶承擔的風險判斷
