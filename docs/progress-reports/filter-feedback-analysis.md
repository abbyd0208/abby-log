## 1. 做了什麼

1. **看了截圖**（`~/Desktop/截圖 2026-08-04 下午1.45.23.png`），確認 Abby 圈起來的是搜尋框下方那張標籤卡片。
2. **讀了現有實作**，定位到程式碼位置：
   - `src/components/BlogBrowser.tsx:60-89` — 篩選卡片（外框 + 三列 chip + 篩選中）
   - `src/components/TagPill.tsx` — chip 樣式
   - `src/lib/site.ts` — `tagGroups` 三層標籤定義
   - `src/app/blog/page.tsx` — 資料流、`?tag=` 參數
3. **把「感覺很重」拆成四個可各自處理的來源**：卡片外框（32px 純空氣內距 + 第二個灰面）、12 顆實心色塊、被分組標籤鎖死的三列、以及讓 chip 變寬的篇數。這一步是為了避免只調高度、結果重量感沒解決。
4. **查了內容面事實**：8 篇文章、12 個有文章的 tag，其中 **5 個 tag 篩完只剩 1 篇**。這支撐「不需要把 12 個 tag 用同等重量攤在首屏」的判斷。
5. **grep 了連帶影響**：`TagPill` 有 3 個使用者（篩選區、`PostCard`、文章頁），確認**不能直接改它的 base style**，否則文章卡片與文章頁的 tag 會被一起改掉。
6. **發現一個方案 3 的實作坑**：tag filter 走 URL 導航（`/blog?tag=`），點完 tag 會換頁、本地 state 重置 → 收合面板選完 tag 會自己收起來，需要額外從 `activeTag` 推導初始狀態。
7. **寫成方案文件**：問題分析、3 案 layout、優缺點、推薦、改檔清單、風險、5 題 PM 決策表。

## 2. 為什麼沒有直接改 code

- **Brief 明確要求**：「這一階段先不要修改 src code，只輸出設計方案文件」「完成後停下來，等待 PM / Abby 決策」。
- **三個方案的取捨不是工程問題，是產品判斷**：要不要為了首屏高度，犧牲三層標籤的分組語意（方案 1）或把篩選入口藏起來（方案 3）？這題只有 Abby 能決定，先做等於幫她決定。
- **Abby 的回饋是感受描述（「佔了上面一大區塊」），不是規格**。直接動手很可能只把高度縮小、但重量感還在，做完還要重來。所以先把「重量從哪來」講清楚，再讓她挑方向。
- 目前工作區已有未 commit 的改動（`src/app/blog/[slug]/page.tsx`、`globals.css`、`Toc.tsx`），這輪不動 src 也順便避免把兩批改動混在一起。

## 3. 推薦下一步

**推薦方案 2（Inline minimal chips）**：拆掉卡片外框、chip 改成未選取無底色／選取才實心、尺寸縮一階、「篩選中」併進「共 N 篇」那列。

理由摘要（完整版在方案文件 §4）：
- 重量的最大來源是外框 + 實心色塊，方案 2 正面處理，不是只縮高度；
- 三層標籤結構完整保留，不用為視覺犧牲資訊架構；
- 純樣式改動、無新 state、無 popover，**風險最低也最容易反悔**；
- 8 篇文章的規模還用不到收合／popover，先上等於提前付互動成本。

如果做完還嫌大，再疊上方案 1 的「更多篩選」把類型／工具兩列收起來——那是加法，方案 2 不會白做。**這一步等看過實際畫面再決定，本輪不預做。**

Abby 一決定方向，實作會走：改 code → lint / typecheck → 起 dev server → 自檢截圖（含 375px mobile）→ 開 dev Chrome 給 Abby 驗收 → 驗收 OK 才問要不要 commit。預估 1 小時內可給畫面（方案 2；方案 1 / 3 因為要處理互動與狀態，會多一些）。
