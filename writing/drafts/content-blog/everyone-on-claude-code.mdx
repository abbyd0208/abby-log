上次使用了Antigravity之後，本來想要一心一意就用他開始工作了，但後來老闆用了Claude code之後整個大愛上，於是開始在內部推起，也幫大家直上了Pro max方案。

自從直上了Pro max方案，我的工作內容也開始些微調整了，變成我可以直接進到專案的Repo裡面改介面，我真的太開心了。

過去在開發時效與還原度之間往往需要妥協，但現在透過 AI 直接介入代碼層，我可以親手填補這道鴻溝。現在有了Promax，我直接vibe coding調到滿意為止！

最近有一個新嘗試，在一個舊有專案內，把一個chat的聊天介面，包含了附加選單的內容、對話的Streaming過程，到互動式修訂的Edit Blcok，從我這邊vibe code出UI介面之後，直接讓LLM工程師接手串AI服務到可以本地測試，前後大約是四天的時間，這種「設計即開發」的流程極大地提升了交付效率！

我的做法是這樣：

1.  把跟LLM工程師討論的內容利用之前製作的skill 『product-architect』
    讓 Claude code產生一份PRD。
2.  拉下這個專案的Repo並且先讓claude code讀取整份專案的程式碼，讓我對專案有大致上的了解。
3.  跟他說我要新增頁面的範圍，請他根據我的PRD 利用之前製作的『Design-Guildline』skill 先把UI Component產出來，先不要串頁面邏輯，因為我要先調設計。
4.  確定每個Component都沒問題，設計也是我滿意的，再將整個UI互動邏輯串起來。

上面提到的product-architect skill 是我之前會放在Gemini上自定義的GEM，主要是幫我釐清產品需求以及產PRD的 skill，這份只是請他幫我改寫格式，並且拆分不同工作階段的Skill。

而 Design-Guildline 是我之前把專案UI Library 的 Figma Token載下來之後，讓Claude 用他的 /Skill Creator 功能製作的，做得非常詳細！除了有顏色的用法之外，還有每個component的用法，除了一個主要的Skill.md之外，還有一些sub-modules，真的很厲害！

![](/images/everyone-on-claude-code/02.png)

這次就先記錄到這邊，關於skill的建立感覺還有很多學問，究竟 Skill 的邊界該劃在哪裡？是該事無巨細地定義規範，還是僅提供核心設計原則？目前的體悟是，這取決於你想要 LLM 扮演的角色。

-   **「詳細」是為了建立約束力：** 像是我把 Figma Token 餵給 Design-Guideline，這種詳細是必須的。因為顏色、間距、組件命名是專案的「硬規則」，如果只寫原則（如：要看起來乾淨），AI 給出的代碼可能每次都長得不一樣。**細節是為了維持一致性。**
-   **「原則」是為了保留創造力：** 而在 product-architect 階段，我更傾向於寫原則。AI 的優勢在於它可以從不同角度切入問題，如果限制太死（例如：登入頁面必須有三個按鈕），反而限制了它幫我優化邏輯的空間。**原則是為了激發可能性。**

如果你剛開始嘗試，我非常推薦從 Claude 的 /Skill Creator 開始。讓 AI 幫你寫出第一版框架，你再進去把那些「絕對不能妥協」的細節填補起來。
