## 種子 1：調度者不動手，才是多 Agent 工作流的核心

**暫定標題**  
《多 Agent 工作流裡，最重要的人不是最會寫 code 的那個》

**角度**  
從「調度者／執行者」分工切入：為什麼一個 AI agent 如果又派工、又自己下去改東西，很容易失去全局；真正穩定的多代理系統，反而需要一個只讀、判斷、派工、盯進度、回報的人。

**為什麼值得寫**  
- 這是 Abby 近期 AI 工作流實驗裡最有辨識度的觀點：不是「多開幾個 agent」而已，而是重新定義誰能動手、誰只能調度。  
- 可連到工作中常見痛點：任務一多，AI 會忘記全局、跨任務污染、改錯範圍。  
- 讀者不需要知道任何客戶產品背景，也能理解「調度者不動手」這條規則的價值。  
- 可以接在既有的多代理文章之後，作為更成熟的一篇「架構反思」。

**素材來源**  
近期 AI agent 系統筆記、調度者／執行者分工筆記、常駐 agent 與一般 subagent 的差異整理。

**公開風險**  
低。只要避開實際專案名稱、內部任務內容、分支與路徑，可以完全寫成通用 AI 工作流方法論。

## 種子 2：AI 記憶系統的重點不是記得更多，而是放對地方

**暫定標題**  
《我後來發現，AI 記憶系統最怕的不是忘記，是記錯地方》

**角度**  
從「記憶分流」切入：易變狀態、長期偏好、專案知識、調查報告、任務備註，應該放在不同層級；記憶系統真正要解的問題不是容量，而是歸屬、時效與污染。

**為什麼值得寫**  
- 跟 Abby 已經寫過的 AI 記憶主題有延續性，但這篇可以往更實作的方向推進。  
- 有一個很好懂的核心句：「放錯地方比沒寫還糟。」  
- 很適合做成圖：  
  - 易變狀態 vs durable knowledge  
  - 私有策略 vs 專案共享知識  
  - append-only 流水帳 vs 定期改寫  
- 對正在做 AI agent、個人知識庫、工作流自動化的人都有用。

**素材來源**  
近期 agent 記憶模型筆記、個人知識中心／記憶儀表板資料層說明、既有 AI 記憶文章脈絡。

**公開風險**  
低到中。概念本身可公開，但素材裡有本機資料層、私有記憶、工作狀態與專案描述，寫作時必須只抽象化「分流原則」，不要引用實際記憶內容或任何工作狀態細節。

## 種子 3：寫作筆記跟開發日誌為什麼要分家？

**暫定標題**  
《我把開發日誌搬回 repo：寫作歸寫作，決策紀錄歸版本歷史》

**角度**  
從一個小但很實用的工作流決策切入：當一份筆記其實在記錄 commit、分支、技術決策與演進脈絡，它就不適合只待在寫作／學習筆記裡，而應該回到 repo，跟 code 一起有版本歷史。

**為什麼值得寫**  
- 這是一個很 Abby.log 的題目：不是大理論，而是工作流裡突然發現「這個東西放錯地方了」。  
- 可以延伸出一個通用判準：  
  - 寫作素材放在寫作系統  
  - 開發決策放在 repo  
  - 長期原則整理成 evergreen note  
  - 任務狀態不要混進公開寫作素材  
- 對用 Obsidian、Notion、repo docs、AI 記憶系統混搭的人很有用。

**素材來源**  
近期開發日誌搬遷筆記、AI 判斷訓練／agent 實驗相關筆記。

**公開風險**  
低。不要寫實際 repo 名、commit、分支、任務細節即可。重點放在「資訊該住哪裡」的工作流判斷。
