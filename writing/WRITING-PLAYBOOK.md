# 寫作 Playbook

> 寫「我怎麼跟 AI 工作」這類文章時的結構樣板與素材規範。
>
> **與 `AGENTS.md` 的分工**：`AGENTS.md` 是每次自動載入的短規格（frontmatter、標籤池、句法層的慣例）。這份是要動筆時才讀的長文件——**文章形狀怎麼選、素材什麼時候採、採什麼**。
>
> 依據：8 篇已發布文章、三場改稿對話（2026-06-30 / 07-19 / 07-20）、以及參考文 [工作紀錄 EP1](https://medium.com/@leo2233445/工作紀錄-ep1-怎麼讓ai讀懂我的flow-20d7b5191388) 的架構。

## 0. 一分鐘版

| | |
|---|---|
| **讀者** | 正在學 vibe coding、還在找工作流的 UI/UX 設計師 |
| **可信度來源** | 「這是我真的做過的事」——具體性是唯一護城河，別為了通用而抽掉 |
| **結構** | 兩套樣板：**A 實驗紀錄型**（單一嘗試，2 週內）／**B 方法論型**（跑完一整個專案） |
| **素材** | 邊做邊採，**不是寫的時候回頭挖**。最貴的一項是「第一版失敗的 prompt」 |
| **流程** | Medium 先發 → 回收進 blog（`canonical` 指回原文） |
| **紅線** | 內部資訊、客戶名、Jira 票號、產品截圖；沒查證過的數字 |

## 1. 風格規範（從三場改稿對話節錄）

### 1.1 語氣：跟同事分享成果報告

原話：「**不要過度自信、不要有中二感，感覺像是在跟同事分享成果報告，保留專業口吻，可以帶點幽默。**」

被實際改掉的用字，當黑名單用：

| 不要 | 改成 |
|---|---|
| 我**終於**找到一套**不會做到崩潰**的工作流 | 我這次改版整理出的工作流（和踩過的坑） |
| 兩個關卡是這套流程的**靈魂** | 最值得分享的部分 |
| 設計**哲學**只有一句 | 其實就一個原則 |
| **最關鍵**的一塊 | **最該補上**的一塊 |
| **最痛、也最值錢**的教訓／被**打臉** | 兩件我做錯被提醒的事 |
| **敢**把規則拿掉／**敢**推翻 | 該推翻就推翻 |

要留的：「老實說」「蠻有意思」「大概會有點用」「給同行參考」這類平視語氣，以及自嘲式幽默（「每次都要重新帶一遍的實習生」「同時製造兩團亂」）。

**戲劇化的獨立短句要節制。** 草稿裡曾有一個單獨成段的「錯了。」（模仿英文寫作的 "Wrong."），發布時被自己拿掉了——中文讀起來太硬。

### 1.2 黑話規則：自建工具一定要解釋

原話：「`/design-flow` 這種是我自己建的 skill，這樣發佈出去別人根本不會知道我在說什麼。」

三段式處理，缺一不可：

1. **可遷移的原則**先講（「照順序、中間會停」）
2. **我具體怎麼做**，並註明這是自建的（「我把這串步驟包成一個叫 `/design-flow` 的 skill」）
3. **「換成你的工具可以怎麼做」**（「你不一定要會建 skill，手動一步一步叫 AI 做效果一樣」）

第 3 點如果做成獨立的框（`> 🔄 換成你的工具`），**全篇最多 4 個**。曾經放到 7 個，被判定「七個一模一樣的格式很吵」，砍到 4 個，其餘寫進正文。

### 1.3 誠實條款

- **不藏失敗。** 文章價值來自「什麼順、什麼卡」的對照。
- **不能把「做過才發現要補」寫成「我早就設計好了，來驗證一下」。** 這條踩過一次：原本想寫「這個專案是我設計完 design-flow 之後拿來驗證的」，查證後發現當時的 skill 標題還叫「全自動」、明寫「Phase 之間不主動停下來問問題」——關卡是專案中途長出來的，不是既有流程的一部分。前者才是真的，也剛好是文章最有價值的地方。
- **不要替自己宣稱查不到的東西。** 同一次還想寫「這些領悟回灌進 skill」，查完 git 發現 skill 至今沒改。最後寫成「工具沒變，變的是我怎麼用它」——更誠實，也更有餘味。
- **降低門檻的自嘲要留。** 發布版自己補了一句「我並沒有用什麼厲害的技術，我就只是把他們都可視化了」——這種話不要在改稿時被「專業化」掉。

### 1.4 不要把同一組結論講三遍

實際踩過：`TL;DR` ＋ `決策方式` ＋ `結論的可複製清單` 三個區塊講同一組原則，「把確認點放在便宜的地方」出現三次。讀者讀到第二次就開始滑。

**規則：同一組原則全篇只出現兩次——開頭 TL;DR ＋ 結尾可複製清單，頭尾呼應就夠。** 中間那節砍掉，只有具體事件支撐的條目才留下、併進困難清單。

### 1.5 最好的內容不要埋在中間

原創度最高的那一節（有具體檔案範例、有「喔！」的洞察）不要排在 60% 的位置。最誠實、最容易被截圖轉發的段落（「我假裝跑過檢查流程，後來被抓包」）不要縮在 blockquote 裡當附註——**升格成正式一節，甚至拉到開場。**

名詞解釋不要擋在最前面。目標讀者多半已經知道 vibe coding 是什麼，剛被開場故事鉤住就被五個定義冷卻是勸退設計。**拆成首次出現時的括號註解，或整段挪到文末當附錄。**

### 1.6 標題法則

> **只有讀過這篇的人才寫得出來的標題。**

這是唯一的判準。中文技術寫作的萬用詞（「踩過的坑」「難的不是 X」）沒有資訊量，換一篇文章也能用。

好的做法是**引用文章裡最尖銳的那句真話**：
- 「我做的 AI 設計工作流叫『全自動』——它最需要的其實是停下來」（引用自己 skill 的標題）
- 「每次對話，AI 都是第一天上班」

副標負責認領讀者與界定範圍：「設計師用 AI 跑完一次完整產品改版，學到的不是怎麼下指令，而是把確認點放在哪」。

### 1.7 紅線

- **內部資訊**：客戶名（寫成「某客戶」）、Jira 票號、內部 PR 編號、Figma 檔名、元件名、專案代號、AI 模型型號 → 拿掉或泛化成「同類產品」「設定頁」。
- **產品截圖**：預設不放。真要放先確認。
- **文字層的產品痕跡**（分支名 `redesign/login`、「這個產品沒有個人專屬空間」）洩漏程度低得多，而且拿掉會傷到具體性——**可以留，但要意識到自己在留**。
- **數字必須查證**。「三週沒看」寫進標題後才發現實際是九天（nightly-digest 第一次跑 7/8，儀表板分頁 7/17 才加）。寫進文章的任何天數、次數、字數，都要有 log 或 commit 佐證。

## 2. 文章結構樣板

### 怎麼選

| | 樣板 A：實驗紀錄型 | 樣板 B：方法論型 |
|---|---|---|
| 適用 | 一個具體嘗試、幾天到兩週 | 跑完一整個專案／半年的累積 |
| 主軸 | 我試了什麼、怎麼失敗、怎麼改對 | 一套可以照著套的流程 |
| 篇幅 | 1,500–2,500 字 | 4,000–6,500 字 |
| 已發布的例子 | 〈全員Claude code〉〈AI 工作流實測〉 | 〈AI Workflow 真的是越自動越好嗎？〉 |
| 系列 | 適合編號（EP1、EP2） | 通常單篇 |

長文（B）在 Medium 很吃視覺呼吸：**每 1,500 字至少一張圖**。

### 樣板 A：實驗紀錄型

骨架取自參考文〈工作紀錄 EP1〉，那篇的形狀很乾淨：

```
（無標題）開場：一句情境痛點，點出「難的不是實作，是 X」
### 為什麼要做這件事？        ← 效益，2–3 條 bullet，不寫背景
### 發想動機                   ← 起因＋界定範圍（「單頁沒問題，整個 flow 呢？」）＋宣告這篇是紀錄
### 我的第一次嘗試             ← 直觀的想法 → prompt 原文 → 失敗結果 bullet → 反思一句
### 第二次嘗試                 ← 找誰討論／查了什麼 → 建議清單 → 我實際調整了什麼 → 素材長怎樣（JSON／截圖）→ prompt 原文
### 成果                       ← 證據截圖＋圖說，一句誠實的自評
### 結論                       ← 一句有邊界的洞見
### Next Step                  ← 還沒解的、想延伸的、致謝
```

**關鍵是「兩次嘗試」的節奏**——第一次直觀地做、失敗、列出為什麼不行，才有第二次。只寫成功那次就變成炫技文。

### 樣板 B：方法論型

`ai-workflow-automation-limits` 最後收斂成的形狀，可以直接沿用：

```
（無標題）開場故事：一個具體場景，最後一句是翻轉
### TL;DR — 三十秒看完        ← 5 條，每條粗體短句起頭
### 01 先看全貌               ← 一張流程圖（自己畫，不要文字流程圖）
### 02 N 個步驟，一步一步走    ### 1. … ### 2. …（每步：原則 → 我怎麼做 → 換成你的工具）
### 03 最該補上的一塊         ← 全篇最原創的那節，放這個位置
### 04 結論：如果你也在找自己的工作流   ← 可複製清單，呼應 TL;DR
### 附錄：文中名詞，一句話版
```

### 兩套共通的硬規則

- **標題階層從 `###` 起跳**，需要更細一層用 `####`。`##` 只在技術示範類文章出現。
- **開場不寫「前言」二字**，直接進情境。兩種開法：情境提問（「如果你在 SaaS 公司工作過，你一定知道這個場景」）或共感提問（「你是否也曾出現過這樣的感覺？」）。
- **不要用「前言」「結語」「總結」當標題**，用內容自然收尾。
- **結尾是「給同處境者的建議」**，1/2/3 編號、每點粗體短句起頭，最後一句輕鬆的行動呼籲（「以上感謝收看～」「共勉之！」）。
- **粗體只用在可獨立成立的一句話結論**（「流程能跑，不等於體驗成立。」），不是標關鍵詞。
- **blockquote 只放金句或引用**，不放補充說明。
- **圖片**：`/images/<slug>/01.png` 兩位數編號，下方用斜體寫圖說，語氣可以隨性（「不知道配什麼圖才好，讓GPT產了一個…」）。純示意圖也照放。

## 3. 素材準備規範

### 3.1 什麼時候採

**有意外就記，不是做完才寫。** 判斷條件：

- 被 AI 搞錯過
- 我糾正過它
- 結論被推翻（原本以為 A，做過發現 B）

順利的 session 沒東西可寫，不用勉強記。

### 3.2 五類素材

按「最容易忘掉」排序，第一項最貴：

**① prompt 的失敗版與修正版**（全篇最有價值，也最快消失）

只放最後那版漂亮的 prompt，讀者照抄不會有同樣結果。三件都要記：

1. 第一次下的 prompt **原文**
2. 為什麼不行（列成 bullet，越具體越好——參考文那三條「不需要 skill 也能達成／沒有腳本沒辦法逐一檢查／沒有工具是零設定就能用」寫得很好）
3. 改了哪裡才 work

指令型的 prompt 尤其要保留「感受描述 + 它實際改了什麼」的成對寫法：「這邊的進場效果要多一點速度感」→ AI 去調了 spring 的 stiffness 和 damping。

**② 轉彎的決策時刻**

原話怎麼被點出來的、當天怎麼改的。這些在工作紀錄裡都有，但**要記日期**——後面文章的弧線全靠這條時間軸站住（「開工第四天正要一條龍衝完，被當場問住」）。

**③ 我做錯被抓包的事**

最誠實、最容易被轉發的段落。原封記下對方說的那句話（「怎麼沒先給我看畫面？」）。

**④ 成品證據**

不是產品畫面，是**流程的證據**：狀態板、manifest、測試報告表格、排程狀態列。這類圖沒有內部資訊風險，而且比產品截圖更能支撐論點。

**⑤ 數字**

天數、次數、字數、commit hash。採的時候就順手記來源（哪個 log 的第幾行、哪個 commit），寫文章時要拿出來對。

### 3.3 素材袋的位置與格式

一篇文章的素材放 `writing/seeds/<slug>.md`，格式：

```markdown
# <暫定主題>

- 日期：
- 觸發（哪件意外讓我想記）：

## 我做了什麼

## prompt 第一版
（原文貼上）
為什麼不行：
- 
改了哪裡才 work：

## 轉彎時刻
- YYYY-MM-DD ：被誰／什麼點出 → 當天怎麼改

## 我做錯的事
（對方原話）

## 素材檔
- 截圖／檔案路徑：
- 待打碼：

## 數字（含來源）
- 
```

寫作時 `writing/seeds/<slug>.md` → 文章 → 發 Medium → 回收成 `src/content/blog/<slug>.mdx`。素材袋不刪，它是下一篇的原料。

### 3.4 打碼規則

**在瀏覽器裡對元素套 `filter: blur()` 之後才截圖**，不是事後蓋一層——糊掉的像素從一開始就沒進到檔案裡，原文無法還原。

判斷要不要打碼之前先讀一次畫面上的實際文字：曾經對著記憶中的舊字串算切點，結果把該留的時間戳也糊掉，而實際內容根本不需要打碼。

**整頁都是內部資訊的畫面不要打碼版**——糊完剩一片馬賽克，讀者什麼也讀不到，不如不放；要放就造假資料重跑一次產乾淨畫面。

## 4. 發佈流程與 Medium 平台坑

### 流程

1. `writing/seeds/<slug>.md` 累積素材
2. 寫成 md（Medium 吃 Markdown 比 HTML 順）
3. 貼 Medium 發布
4. 回收成 `src/content/blog/<slug>.mdx`，`canonical` 指回 Medium 原文
5. 圖片進 `public/images/<slug>/`
6. 原稿與素材留 `writing/archive/<slug>/`

### Medium 的坑（都實際踩過）

| 坑 | 處理 |
|---|---|
| 貼上時 heading 語意被剝掉（RTF 變粗體、HTML 連粗體都沒） | 逐行選取後按 `Cmd+Opt+2`（小標）／`Cmd+Opt+1`（大標）。**每套一行就驗一行** |
| Markdown 表格不渲染 | 改成粗體小標＋條列，或截圖 |
| code block 裡中文不對齊（全形空格、box-drawing 字元一定歪） | 改純條列，或截圖 |
| 圖片不能自動帶入（本地路徑無效，import 只吃線上圖床） | 新開草稿貼文字，每個位置手動拖圖 |
| 內文 hashtag 只會變一行灰字 | 刪掉，用 Medium 自己的 tag 系統（發文時選，最多 5 個） |
| 自己寫「約 X 分鐘閱讀」 | 刪掉，Medium 自動算 |
| 破折號被轉成「 — — 」帶空格 | 回收進 blog 時記得還原成 `——` |

Tag 建議組合：前 3 個帶流量（`AI`、`Design`、`Claude`），後 2 個定位讀者（`Productivity`、`知識管理`）。

## 5. 要不要做成 skill／command

**已有決定（2026-07-29）：先手寫三次 seed，欄位穩了再固化。** 理由是先錨定真實任務再做工具——現在做等於在猜自己需要什麼欄位。

所以現在該做的只有一件事：**用上面 3.3 的模板手寫三次**（可以直接複製那段當檔案內容）。三次之後再回來看下面的規格。

### 固化時的規格（待三次 seed 之後）

拆兩支，**不要合成一支**——合成一支，累的時候就不會跑。

**`/article-seed`**（session 尾聲，5 分鐘，只倒素材不寫作）
- 從當前 session 抽出：做了什麼、prompt 的失敗版與修正版、轉彎時刻、被抓包的事、數字
- 寫進 `writing/seeds/<slug>.md`，缺的欄位留空不要編
- **不產文章**。這是它能被跑起來的唯一原因

**`/article-draft`**（想發文才跑）
- 讀 `writing/seeds/<slug>.md` ＋ `AGENTS.md` ＋ 這份 playbook
- 先問樣板 A 還是 B、先確認角度，**再寫**（三場對話裡最順的一次就是「先整理撰寫方向、跟我確認之後，再繼續寫成文章」）
- 產 md 給 Medium 用，發完才回收成 mdx
- 硬規則：數字沒有來源就標 `TBD` 不要自己推；內部資訊主動列出來問

兩支都放 `~/.claude/skills/`（個人用，不進 plugin——這是 Abby 個人寫作流程，不是團隊共用的設計工具）。
