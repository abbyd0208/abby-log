最近我接手了一個新領域的專案，剛開始參與客戶會議時很挫折。客戶太習慣自己的工作流程，會很自然地拋出各種術語。每次他們試著解釋，我還是聽得一頭霧水。不是他們講得不好，是那些詞背後沉澱了一整套我沒有的實務經驗。

遇到這種狀況，設計師的直覺通常是「去查那個詞」。但我很快發現：**問題不在那個詞本身，是我提問的方式錯了**。

> 所有專有名詞的背後，其實都是一個工作流程；而所有工作流程的背後，都藏著一組介面結構。

這篇記錄我怎麼用一套結構化的問法，把一份會議紀錄拆成可以動手設計的介面結構，順便挖出客戶自己都沒察覺的邏輯盲點。先看全貌：

![](/images/prompt-tutor/01.png)

*兩輪的先後關係。中間那排 A／B／C 是整件事的樞紐——分類決定你該去哪查。*

### 用對工具，重構問題

怎麼找到正確的提問方式？我用了自己寫的一個指令——Prompt Tutor。

它在 Claude Code 裡叫 slash command，你可以把它想成一份預先寫好的角色設定，打一個斜線就整份注入這次對話。它的作用不是幫我回答業務問題，而是扮演一個嚴格的 prompt engineering 老師：

```
1.鎖定身份——熟悉官方 prompt 準則的老師，而且明講不准中途切回預設助理人格
2.教學風格——解釋到「背後做了什麼」的機制層。範例：講 prefill 棄用時，說明「model 已能穩定遵守 schema，不需 force start」這個 root cause，而非只說「Claude 4.6+ 拿掉了 prefill」
3.回答前查證——問題若涉及 model 行為、參數、最新最佳實踐時，需查證官方文件後再回答。我貼 prompt 給它看的時候，它不能直接回答，必須先指出 1～3 個問題並引用我的原文、給改寫版、再說明依據哪一條原則
4.碰到值得記下來的東西，我就存起來，這樣可以累積我的學習歷程。
```

### 實際怎麼用呢？

### 雙輪提問：從名詞到畫面

我原本想問的只有一句：

這份會議記錄裡有很多專有名詞我看不懂，幫我解釋casebook是什麼

它沒有回答我，而是先把這個問法退件。指出的根本問題是：只查單字只會拿到字典定義，我應該拿整份會議紀錄，請 AI 先把手上的資料榨乾，做「分類」和「結構萃取」。

**發現的核心 insight：提問結構錯了，就得不到有用的答案。** 我需要用一套有系統的方式，一步步從名詞梳理到介面結構——這就是「雙輪提問」。
每個詞照下面順序處理：
1. 先原文引用文件中提到這個詞的所有句子（含時間戳）
2. 只根據引用內容說明它在這個專案裡的意思；文件沒講清楚就寫「文件未定義」，
   不要用你的一般知識補
3. 分類成：A 說話者自己的定義／類比、B 業界通用詞、C 本產品自造詞
4. 判斷它會影響哪個畫面或元件
5. 若文件有定義，額外抽出「這個詞隱含的介面結構」——
   資料的階層關係、誰能新增／編輯、數量會長到多大
輸出一張表：名詞｜分類｜文件內是否已定義｜隱含的介面結構｜影響的畫面｜我還缺什麼。
最後單獨列一份「只有客戶能回答的問題清單」，每題附上為什麼文件回答不了。
```

「先原文引用再說明」是為了讓我看得出文件到底有沒有講——引用如果是空的，那就是真的沒講，而不是被腦補的定義騙過去。

「掃過全文每一節，包含表格與附註」是因為不明說範圍，它會自己挑覺得重要的段落，我就漏詞。

**A／B／C 分類是整個方法的樞紐：定義權在誰手上，決定你該去哪查。**

- A 類（說話者的定義／類比）：定義權在客戶本人，只能回頭問他，查外部會拿到別人的定義

- B 類（業界通用詞）：定義權在產業，這類才適合查領域網站、法規資料庫、競品

- C 類（產品自造詞）：定義權在自家 PRD，要查團隊內部文件，不是查外面

casebook 就是 A 類。「美國法學院的判例彙編教科書」——定義是對的，但客戶不是在介紹一本書，他是拿它當類比在解釋文件庫該長什麼樣。

### 第二輪：從心智模型到介面設計

名詞盤完了，我進到第二輪——不是用「我現在知道什麼詞」來看介面，而是用「資料結構長什麼樣」來找參考。這時不找同產業的競品，而是找做過類似資料結構的產品。

```
我要設計一個「內部規章知識庫」畫面。它的心智模型是：
- 一層可展開的主題階層目錄（法遵團隊維護、一般員工不可自建）
- 點進主題看底下掛的多份規章原文
- 每個主題最後收斂出一份「該注意什麼」的清單
- 文件量會累積到數十上百份，需要搜尋與篩選
列出 4～6 種你認為結構對得上的產品類型，每種說明：
- 目錄區與內容區怎麼分欄
- 階層深到第幾層開始出問題、它怎麼處理
- 文件數量變多時，搜尋與篩選放在哪
- 「某些節點使用者不可編輯」這種權限差異，介面上怎麼表現
先講你的判斷依據，再給結論。不要列你不確定實際長相的產品。
有工具可用就先搜實際畫面，搜不到再靠推理，並標明哪些是推理。
```

阻止AI先射箭再畫靶的結論、憑印象生成的假競品、有工具卻整段腦補。

### 跑完之後：拿到可以立刻用的三份文件

整個過程跑下來，我手裡拿到三份東西：

**① 執行文件**：結構化的清單

輸入素材有哪些、每份素材的位階、全域規則、兩輪 prompt、每一輪的完成判準。特別重要的是「素材位階表」——同一件事，不同來源講的不一樣時，誰說了算。我的排序是：客戶本人出席並拍板的會議 ＞ 客戶自己動手做的東西 ＞ 他口頭講的類比 ＞ 團隊的內部會議 ＞ 外部參考資料。

沒有這張表，AI 會把五份資料當等重，給你一個平均值——而平均值在需求上通常是錯的。

**② 名詞盤點**：從模糊到精確

加上每個詞「原文引用 → 解讀 → 分類」的逐條紀錄。這輪盤出 16 個名詞，其中 15 個的答案一直都在我手上，只是散在不同段落，我沒把它們接起來。原本以為要問客戶的 8 個問題，最後只剩 3 個。

**③ 介面 pattern 研究**：跨產業的設計參考

它把心智模型拆成六條結構特徵（目錄誰能編、階層能不能改、同一批內容要服務幾種用途⋯⋯），然後宣告：任何產品只要同時滿足這幾條就算對得上，跟它賣什麼無關。

我讓它接了 Mobbin 的 MCP，所以每一條觀察後面都掛著實際的產品畫面，不是憑印象寫的描述。沒有這類工具也沒差——把 prompt 最後一句改成「標明哪些是你的推理」，再自己去開那幾個網站對一遍就好。

### 核心心得：提問結構比提問內容更重要

做完這個實驗，我看到了一些值得提煉的東西：

**先把手上的文件問完，再去查外面。** 大部分答案其實都在會議紀錄裡，只是散在不同段落。通過結構化盤點，我把專有名詞的定義都列舉出來了——這比直接問「什麼是 casebook」更有用。

**把「我不懂就沒辦法設計」當成篩選條件。** 不是所有術語都要弄懂，只有會影響介面結構的才要。這條讓盤點不會變成無底洞。

**同一種介面結構，會跨產業重複出現。** 我卡住的那個問題，別的領域可能早就解過了。反過來，我解出來的東西也不會只有這個產業用得到——所以找參考不要只看同業競品。

另外兩件特別值得學：它明寫哪些產品沒有納入、為什麼（找不到可靠的實際畫面就不列，不憑印象描述），也明寫這輪研究的限制（哪一題沒找到實例、答案純粹是推理）。一份會誠實說自己哪裡沒做到的研究，才敢拿去當設計依據。

### 這對 AI 工作流意味著什麼

這個過程之所以能跑通，核心不在 AI 有多聰明，而在於把自己的需求表達得有多清楚。

用 Prompt Tutor 的經驗讓我理解到：AI 不會自動幫你補齊資訊、找出邏輯盲點。反過來，**當你能精確地告訴它「標出引用、註明推理、誠實說明限制」時，它才能給你一份可信的成果**。

這不是在 prompt 裡堆砌更多指令，而是在設計一套「驗證的框架」——讓雜亂的素材通過結構化的篩選、讓隱藏的假設被迫浮上檯面、讓 AI 的每一步推理都能溯源。

下一步我想試的方向是：能不能把這套方法推廣到其他領域——需求文件、技術規格、市場研究。如果模式成立，就代表**用 AI 工作的本質其實是在練習「怎麼問問題」**，而不是在「怎麼用 AI」。
