### ① 把「AI 使用規則」當成可驗證假設，而不是憑感覺寫進手冊

**角度**  
不是每條工作流教訓都該直接變成規則。可以把候選規則拆成小型 A/B 任務，用 baseline vs 套規則版比較：哪種真的改善輸出？哪種只是在增加流程成本？

**為什麼值得寫**  
這題很像 Abby.log 會有的「AI 工作流實驗紀錄」：  
- 有真實踩坑背景，但可以抽掉任務細節，只講驗證方法。  
- 核心不是某個專案，而是「怎麼避免把一次事故過度制度化」。  
- 可以延伸成一篇很實用的文章：  
  - 哪些規則適合全域收？  
  - 哪些規則應該縮窄到特定產物？  
  - 哪些規則其實只是「當下很痛」但沒有足夠證據？

**素材來源**  
本週產出的規則驗證報告、AI 工作流收件匣裡的候選規則整理。

**公開風險**  
🟡 中低。  
可公開的是「驗證方法」與「規則收斂框架」；不可公開的是報告裡牽涉的真實任務內容、內部檔案、專案背景、PR/Jira/客戶文件等。寫作時需要只保留抽象化流程，不放原始案例細節。

### ② 寫東西前先讀範例，什麼時候有用？什麼時候反而沒用？

**角度**  
「寫任何文字產出前先讀 2–3 個近期範例」聽起來很合理，但這次驗證結果其實更細：  
- 對有 Abby 個人體例、很難用規格講清楚的產物，讀範例很有用。  
- 對格式已經很清楚的產物，讀範例可能只是模仿表面，反而稀釋內容。

**為什麼值得寫**  
這是一個很適合公開的 AI 寫作 / AI 協作方法題。它不是「多給範例就會變好」這種泛泛建議，而是有判準：  
- 體例能不能被規格化？  
- 產物重點是語氣節奏，還是判斷邊界？  
- 範例是在補上下文，還是在製造風格污染？

這篇可以寫成：「Few-shot prompt 不是萬用藥：我怎麼判斷什麼時候該給範例」。

**素材來源**  
規則驗證報告中的 A/B 結果、AI 工作流收件匣裡的文字產出規則候選。

**公開風險**  
🟢 低。  
只要不引用原始任務與內部文字內容，這題可以完全寫成通用 prompt / writing workflow 方法論。

### ③ 個人 AI 記憶系統的整理痛點：什麼該留成規則，什麼該刪掉？

**角度**  
今天的工作狀態裡出現一條很有意思的線：Abby 開始回頭整理既有記憶規則，包含「哪些 workflow memory 已經不想要了」、「什麼時候該用手冊管理」、「規則該放在哪一層」。

可以寫成一篇比較 meta 的文章：  
「AI 記憶不是越多越好：我的個人 agent 記憶系統怎麼做修剪」。

**為什麼值得寫**  
這題跟 Abby 的長期主題很一致：個人 AI 記憶、工作狀態系統、Hermes / Claude Code 的協作方式。  
可寫重點：  
- 記憶會老化。  
- 規則太多會互相打架。  
- 有些東西應該是 skill / 手冊，不該塞進長期 memory。  
- 刪除規則本身也是系統設計的一部分。

**素材來源**

**公開風險**  
🟡 中低。  
題目本身可公開，但不要展示實際 memory 檔名、內部規則全文、專案相關規則內容。適合用「規則老化」與「記憶分層」做概念文章。
