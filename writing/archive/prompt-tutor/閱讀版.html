Prompt 到底該怎麼下才能拳拳到肉？我用 AI 破解專利律師的領域知識迷宮

不是查那個詞的意思，是先改我問問題的方式。附我實際用的兩輪 prompt

最近我接手了一個給專利律師用的平台專案。

剛開始參與客戶會議時很挫折。律師們太習慣自己的工作流程，會很自然地拋出各種術語——casebook、「答辯狀」、審查基準。每次他們試著解釋，我還是聽得一頭霧水。不是他們講得不好，是那些詞背後沉澱了一整套我沒有的實務經驗。

遇到這種狀況，設計師的直覺通常是「去查那個詞」。但我很快發現：問題不在那個詞本身，是我提問的結構。

所有專有名詞的背後，其實都是一個工作流程；而所有工作流程的背後，都藏著一組介面結構。

這篇記錄我怎麼用一套結構化的問法，把一份會議紀錄拆成可以動手設計的介面結構，順便挖出客戶自己都沒察覺的邏輯盲點。先看全貌：

我的幕後推手：Prompt Tutor

在 Google 那個詞之前，我先切到自己寫的一支指令 —— Prompt Tutor。

它在 Claude Code 裡叫 slash command，你可以把它想成一份預先寫好的角色設定，打一個斜線就整份注入這次對話。它的作用不是幫我回答業務問題，而是扮演一個嚴格的 prompt engineering 老師：

  1. 鎖定身份——熟悉官方 prompt 準則的老師，而且明講不准中途切回預設助理人格
  2. 教學風格——解釋到「背後做了什麼」的機制層。範例：講 prefill 棄用時，說明「model 已能穩定遵守 schema，不需 force start」這個 root cause，而非只說「Claude 4.6+ 拿掉了 prefill」
  3. 回答前查證——問題若涉及 model 行為、參數、最新最佳實踐時，需查證官方文件後再回答。我貼 prompt 給它看的時候，它不能直接回答，必須先指出 1～3 個問題並引用我的原文、給改寫版、再說明依據哪一條原則

並且如果這個是一個值得學習的筆記，幫我存到指定地點，這樣可以累積我的學習歷程。

回到正題，在這個案例，我怎麼使用呢？

我原本想問的只有一句：

這份會議記錄裡有很多專有名詞我看不懂，幫我解釋 casebook 是什麼

它沒有回答我，而是先把這個問法退件。 指出的根本問題是：只查單字只會拿到字典定義，我應該拿整份會議紀錄，請 AI 先把手上的資料榨乾，做「分類」和「結構萃取」。

🔄 換成你的工具：不一定要寫 slash command。開對話時先貼一段「你是熟悉 prompt engineering 的老師，我貼 prompt 給你的時候，先指出問題、再給改寫版、最後說依據哪條原則」，效果一樣，只是每次都要重貼。等你發現自己貼第三次了，再考慮把它固定下來。

雙輪提問：從名詞到畫面

第一輪：詞義盤點與定義權分類

第一輪不設計畫面，只做兩件事：把名詞分類，把它隱含的介面結構抽出來。

<meeting_notes>
（貼整份會議紀錄，或給檔案路徑）
</meeting_notes>

我是負責這個產品介面的 UI/UX 設計師，不熟 ◯◯ 領域。
盤點上面這份會議紀錄裡「我不懂就沒辦法設計介面」的所有名詞——
掃過全文每一節，包含表格、action items 與附註，不要只挑前面幾段。

每個詞照下面順序處理：
1. 先原文引用文件中提到這個詞的所有句子（含時間戳）
2. 只根據引用內容說明它在這個專案裡的意思；文件沒講清楚就寫「文件未定義」，
   不要用你的一般知識補
3. 分類成：A 說話者自己的定義／類比、B 業界通用詞、C 本產品自造詞
4. 判斷它會影響哪個畫面或元件
5. 若文件有定義，額外抽出「這個詞隱含的介面結構」——
   資料的階層關係、誰能新增／編輯、數量會長到多大

輸出一張表：名詞｜分類｜文件內是否已定義｜隱含的介面結構｜影響的畫面｜我還缺什麼。
最後單獨列一份「只有客戶能回答的問題清單」，每題附上為什麼文件回答不了。

裡面每一句都在擋一種失敗。「先原文引用再說明」是為了讓我看得出文件到底有沒有講——引用如果是空的，那就是真的沒講，而不是被腦補的定義騙過去。「掃過全文每一節，包含表格與附註」是因為不明說範圍，它會自己挑覺得重要的段落，我就漏詞。

而 A／B／C 這欄是整張表的樞紐：定義權在誰手上，決定你該去哪查。

  • A 類（說話者的定義／類比）：定義權在客戶本人，只能回頭問他，查外部會拿到別人的定義
  • B 類（業界通用詞）：定義權在產業，這類才適合查領域網站、法規資料庫、競品
  • C 類（產品自造詞）：定義權在自家 PRD，要查團隊內部文件，不是查外面

casebook 就是 A 類。「美國法學院的判例彙編教科書」——定義是對的，但客戶不是在介紹一本書，他是拿它當類比在解釋文件庫該長什麼樣。

第二輪：把心智模型接到介面 pattern

第一輪定稿之後，我補了一句：

但我查了詞是什麼意思之後，我還是要查畫面長什麼樣子。

第二輪就是這句話逼出來的。 而答案不是「那就一起問」——是這兩件事要分兩次問，而且有先後：詞義是查畫面的輸入。

我不知道 casebook =「階層目錄 → 案例 → 收斂成注意事項」的時候，拿這個詞去介面參考網站搜是零筆；知道之後，關鍵字才變成 hierarchical doc navigation、knowledge base with nested topics——這才搜得到東西。

所以第二輪要做的是拋開領域包袱，去找資料結構相同的介面，而不是找同產業的競品。

下面這段的心智模型我換成一個跟實際案子無關的例子，你自己用的時候把它替換成第一輪抽出來的那組就好：

我要設計一個「內部規章知識庫」畫面。它的心智模型是：
- 一層可展開的主題階層目錄（法遵團隊維護、一般員工不可自建）
- 點進主題看底下掛的多份規章原文
- 每個主題最後收斂出一份「該注意什麼」的清單
- 文件量會累積到數十上百份，需要搜尋與篩選

列出 4～6 種你認為結構對得上的產品類型（例如法規資料庫、技術文件站、
知識庫工具⋯⋯），每種說明：
- 目錄區與內容區怎麼分欄
- 階層深到第幾層開始出問題、它怎麼處理
- 文件數量變多時，搜尋與篩選放在哪
- 「某些節點使用者不可編輯」這種權限差異，介面上怎麼表現

先講你的判斷依據，再給結論。不要列你不確定實際長相的產品。
有工具可用就先搜實際畫面，搜不到再靠推理，並標明哪些是推理。

最後三句分別擋掉三種失敗：先射箭再畫靶的結論、憑印象生成的假競品、有工具卻整段腦補。

跑完之後，我拿到三份文件

① 執行文件——因為我沒有直接下 prompt

先寫一份執行文件：輸入素材有哪些、每份素材的位階、全域規則（違反即重來）、兩輪 prompt 全文、每一輪的完成判準長什麼樣。有這份，這件事才能過夜跑，也才能之後重跑。

裡面最有用的是素材位階表：同一件事，不同來源講的不一樣時，誰說了算。我的排序是——客戶本人出席並拍板的會議 ＞ 客戶自己動手做的東西 ＞ 他口頭講的類比 ＞ 他沒出席的內部會議 ＞ 外部參考資料。

沒有這張表，AI 會把五份資料當成等重，然後給你一個平均值。而平均值在需求上通常是錯的。

② 名詞盤點——就是前面那兩張表

加上每個詞「原文引用 → 解讀 → 分類」的逐條紀錄。這輪盤出 16 個名詞，其中 15 個的答案一直都在我手上，只是散在不同段落、我沒把它們接起來；原本以為要問客戶的 8 個問題，最後只剩 3 個。

③ 介面 pattern 研究——第二輪的產出

它把心智模型拆成六條結構特徵（目錄誰能編、階層能不能改、葉節點的量級、分布均不均、同一批內容要服務幾種用途⋯⋯），然後宣告：任何產品只要同時滿足這幾條就算對得上，跟它賣什麼無關。

我讓它接了 Mobbin 的 MCP，所以每一條觀察後面都掛著一個實際的產品畫面，不是憑印象寫的描述。

另外兩件我覺得值得學起來：它明寫哪些產品沒有納入、為什麼（找不到可靠的實際畫面就不列，不憑印象描述），也明寫這輪研究的限制（哪一題沒找到實例、答案純粹是推理）。一份會誠實說自己哪裡沒做到的研究，才敢拿去當設計依據。

如果你也接了一個完全不熟的領域

我原本以為這次的瓶頸是「我不懂法律專有名詞」。做完才發現，真正的缺口是：客戶說的「理所當然」，正好是我不知道的那部分。 而理所當然的東西不會出現在會議紀錄裡，要主動去挖。

三件我會再用一次的：

  1. 先榨乾手上的文件，再決定要不要外求。 定義權在誰手上，決定你該去哪查——客戶自己發明的類比，只能回頭問他本人。
  2. 把「我不懂就沒辦法設計」當成篩選條件。 不是所有術語都要弄懂，只有會影響介面結構的才要。這條讓盤點不會變成無底洞。
  3. 「不知道自己不知道」只能靠整批盤點解決。 一次問一個詞，永遠只能處理你已經注意到的那些。

我們不需要成為半個專利律師。設計師的價值是把混沌的領域知識翻成介面語言，而第一步是先把問題問對。

那份「只有客戶能回答的問題清單」可以直接拿去當下次的會議議程，我這次就是這樣用的。
