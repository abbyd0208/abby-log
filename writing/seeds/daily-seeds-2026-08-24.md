### 種子 1：搜尋回 0 筆不是證據：AI Agent 做稽核前要先驗搜尋工具本身

**角度**  
從一次「搜尋語法靜默失效」的踩坑出發，寫 AI / Claude Code 在做盤點、稽核、修復驗證時，不能把「搜尋回 0 筆」直接當成「問題不存在／已修好」。真正可靠的流程應該是：先用放寬版查詢確認搜尋管道有效，再收窄條件。

**為什麼值得寫**  
- 這是很常見、但很容易被忽略的 AI 工作流錯誤：工具沒有報錯，模型就會把空結果當事實。
- 可以做成一篇實用短文：  
  「否定性結論也要驗證」→「先證明搜尋工具有命中能力」→「再相信 0 筆結果」。
- 對 Claude Code / coding agent / 自動 QA 都很有用，不需要任何客戶產品背景。

**素材來源**  
- 近期的規則驗證報告  
- 工作流收件匣裡新增的「搜尋回 0 筆不等於沒問題」規則候選  
- 報告中已有可重現的最小實驗與對照結果，可直接轉成文章核心案例

**公開風險**  
低。只要不提原始事故所在的專案、檔名、設計 token 細節，就可以完全寫成通用 AI 工具驗證方法。

---

### 種子 2：可重現的稽核報告：不要只問 AI「有沒有修好」，要讓第二個人重跑得出來

**角度**  
寫一套「AI 產出稽核報告」的可靠格式：釘住版本、每條結論附可重跑指令與原始輸出、最後由獨立驗證者重跑，標出哪些可重現、哪些只能標 UNVERIFIED。

**為什麼值得寫**  
- 這是 Abby.log 很適合的主題：不是單純教工具，而是把 AI 協作變成可驗收流程。
- 可以連到「AI 不是不能做稽核，而是稽核結果要可重現」這個核心觀點。
- 適合做成 checklist / template，讀者可以直接套用。

**素材來源**  
- 近期工作流收件匣新增的「稽核／盤點類任務要做成可重現成品」筆記  
- 規則驗證報告裡的證據區格式  
- 已有的 AI 工作流反思脈絡

**公開風險**  
低到中。方法本身可公開；但文章不能引用原始專案盤點內容、內部元件、實際檔名、分支或任務來源。建議改用自造 mini repo 或抽象範例展示。

### 種子 3：平行派 Agent 不是只開 Worktree：還要分 port、擁有檔案與停滯看門狗

**角度**  
延伸多 agent / Claude Code 平行工作流：worktree 只能解決「檔案隔離」的一部分，真正要讓多個 agent 同時跑，還要處理 port 衝突、檔案 ownership、任務重疊分析，以及卡住時怎麼重派或標 blocked。

**為什麼值得寫**  
- 這是 Abby 近期 AI 工作流演進裡很有辨識度的題目。
- 比「我用了多 agent」更進一步，進到 operational layer：多個 agent 怎麼不互撞、怎麼驗收、怎麼處理停滯。
- 可和既有的 Hermes / Telegram / 多代理文章形成系列延伸。

**素材來源**  
- 工作流收件匣新增的「艦隊式平行」筆記  
- 既有多代理協作、worktree、盲評 judge agent 的工作流沉澱

**公開風險**  
中低。概念可公開，但不要引用任何實際專案、repo、port、分支、任務清單或客戶需求內容。建議用「三個假想 agent 同時修改 demo app」來示範。
